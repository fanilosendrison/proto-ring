# Proto-Ring API-01 — Agent-first public API v1

**Status:** Candidate specification, version `0.1.0` — **NOT APPROVED**, **NOT IMPLEMENTED**, **NOT INDEPENDENTLY QUALIFIED**\
**Owner:** Proto-Ring #134 (API-01); downstream implementation #135/#136, qualification #137, parent #28\
**Inspected source:** `fanilosendrison/proto-ring@1eb84e1b4474b155d2271d1decb66d0cd86a555f` (2026-11-03)\
**Wire protocol:** `api_version: 1`; JSON Schema Draft 2020-12\
**Companion files:** `schemas/api.schema.json`, `schemas/request.schema.json`, `schemas/response.schema.json`, `schemas/local-context.schema.json`, `examples/`, `conformance/`.

This document is a **candidate public-interface contract**. It does not supersede existing accepted language-neutral governance contracts, change RGM or RGS versions, complete #134, authorize implementation or assert any passed hostile review. The public façade must preserve the accepted semantics of RepositoryState, RepositoryGovernanceState, Governance Authority, governed objects, Governance Bindings, Repository Integrity, projections and evidence requirements. The old migration-only `proto-ring-compat` transport is neither an authority nor an ongoing compatibility gate. Existing consumer-owned pins to historical exact commits are not changed.

## 1. Purpose and governing principles

The primary consumers are coding agents in active repository sessions (Pi, Claude Code, Codex and equivalents), with humans and other clients also supported. A public operation must be discoverable, structurally typed, effect-explicit and callable without consulting implementation-private engine modules. Agents select targeted or complete information; Proto-Ring MUST NOT impose inferred relevance filters, hidden summaries, inferred validation membership or silent output truncation. A requested complete view either contains all values within its precisely declared scope or returns a controlled explicit failure.

There are **distinct authorities**: the consumer owns policy and the RI validation profile; a host owns admission, runtime realizations, credentials and actual execution effects; the existing engine owns canonical loading, selection, observation, evaluation and verdict. The agent owns its requests, not privileged permission. A log is an observation, not another RI verdict or an instruction. A single completed check has **one canonical CheckReceipt**.

* **No universal `check_all`**. The engine-module/legacy-adapter inventory does not imply public operations or mandatory obligations.
* **No repair, adoption, bootstrap mutation, generation, historical replay, implicit provider network observation or hidden command execution** in v1.
* `open`/`inspect`/declaration-based `explain` may perform local Git observation subprocesses but MUST NOT execute consumer validators, generators or provider requests.
* A check may execute arbitrary code under its effective local OS permissions; `read-only governance` is **not** a promise of physical mutation prevention.
* No new RGM capability is created. Missing/undeclared/unknown/inapplicable and RI `SATISFIED`/`VIOLATED`/`UNDETERMINED`/`PASS`/`NON_PASS` MUST remain separate.

## 2. Public operation catalog (closed v1)

| Wire operation | Rust surface | Effects | Preconditions | Result |
|---|---|---|---|---|
| `discover` | `discover()` | Pure metadata | v1 supported | Finite operation catalog with full machine-readable request and response schemas |
| `inspect` | `open(repository).inspect(selector)` | Local governance observation/Git reads; no consumer validators or network | RGS load succeeds; repository readable/authorized | One state-bound typed inspection |
| `explain` | `GovernanceObservation.explain(query)` | Local governance observation for standalone CLI; pure projection on loaded Rust observation | RGS load and query resolution | Deterministic structured facts, no inferred consumer meaning |
| `check_repository_integrity` | `check_repository_integrity(request, host)` | Local observation and explicit consumer command execution | RI declared, complete plan admitted, required host guarantees available | One canonical `CheckReceipt` or explicit non-verdict outcome |
| `read_execution_output` | `read_execution_output(request, custodian)` | Protected local artifact read; **no command execution** | Authorized retained receipt and output | Exact captured byte range, no new verdict |

`open` is an in-process typed Rust constructor, **not** a sixth wire operation and not a persistent process session. Every standalone JSON/CLI `inspect`/`explain`/`check` separately establishes current observations. Later MCP/HTTP/other language adapters may wrap these contracts but are not required in v1. Accepted ADR Body Immutability, Git Whitespace, Exact Evidence Binding and GitHub ARM **are not independently invocable public v1 operations**; their existing engine mechanisms are not removed.

`discover` MUST return exactly these five operations, with each operation's schema complete and self-contained in the discovery response or equivalently bundled in that same returned self-contained schema document; no external network or repo-prose fetch is required to interpret the schema. Each entry describes effects, preconditions, applicability and authorization **separately**. Catalog membership states `SUPPORTED`; it neither discovers consumer applicability nor authorizes execution. Schema objects returned by discovery MUST validate against the JSON Schema 2020-12 metaschema. The files in `schemas/` are the candidate machine-readable definitions and must be made observationally identical to the published discovery payload.

## 3. Protocol envelope, errors and versioning

Every JSON invocation consists of **one UTF-8 request object on stdin, one UTF-8 response object on stdout followed by one LF**, then process exit. No daemon, shared in-memory session, implicit cached governance state, streaming JSON lines, HTTP or remote service. Validator stdout/stderr never contaminate protocol stdout. CLI convenience verbs construct the same requests and use the same projection and evaluation code.

Request grammar is the disjoint union by `operation` in `schemas/request.schema.json`. Required envelope: `api_version` (exact JSON integer `1`), `operation` (one of five names), `input` (operation-specific object). All listed properties are required unless explicitly optional in the schema; no unknown fields, unknown enum values, duplicate keys at **any** JSON object depth, NaN, Infinity, implicit type conversions or malformed UTF-8. Duplicate keys MUST be rejected **before** decoding into maps; JSON Schema cannot detect keys already collapsed by a decoder. Whole request maximum: **1 MiB** (1,048,576 bytes), a resource limit, not a semantic governor. An error MUST be explicit; no request truncation.

Successful response grammar: `{ "api_version":1, "operation":..., "outcome":"result", "value":... }`. Non-result grammar: `{ "api_version":1, "operation": <name-or-null>, "outcome": <failure-discriminant>, "error":{...} }`. `value` and `error` never coexist. `operation:null` is permitted only when a malformed request cannot be assigned to an operation. Stable `outcome`: `result`, `inapplicable`, `not_found`, `admission_refused`, `stale_observation`, `incomparable_observation`, `controlled_failure`, `execution_incomplete`, `protocol_error`.

Stable error codes for v1: `invalid_request`, `unsupported_version`, `response_too_large`, `governance_load_failed`, `repository_integrity_not_declared`, `component_not_declared`, `subject_not_found`, `repository_not_authorized`, `profile_not_authorized`, `execution_plan_not_authorized`, `execution_guarantee_unavailable`, `local_context_invalid`, `stale_observation`, `incomparable_observation`, `output_not_started`, `output_expired`, `output_access_refused`, `output_unavailable`, `range_not_retained`, `invalid_output_range`, `execution_incomplete`, `receipt_persistence_failed`, `internal_failure`. The outer `outcome` and inner `code` MUST agree with the operation's corresponding semantics; neither code nor process exit supplies an RI verdict.

`error.stage` is either `null` or an exact existing `RepositoryGovernanceStage` (`repository_state`, `bootstrap`, `repository_governance_model`, `governance_authority`, `governed_objects`, `governance_bindings`, `repository_integrity`, `projection_integrity`, `evidence_requirements`, `composition`). `error.detail` is non-normative nullable text and MUST NOT be parsed to synthesize a stable category; privileged hosts may redact it. `error.attempt_id` and `error.effects_possible` are explicitly nullable and meaningful for incomplete attempts. A controlled RGS load failure never returns a partial RGS.

Exit code **0** means a structured protocol response was successfully emitted, including a returned RI `NON_PASS`, admission refusal or `execution_incomplete`. Exit **2** means invalid wire request. Exit **70** means an internal failure prevented normal structured processing; an exit code alone cannot prove no commands started. No automatic retry after an unknown potentially effectful attempt. Response maximum: **16 MiB** (16,777,216 encoded bytes). A requested complete view exceeding this limit MUST produce `response_too_large`, not a successful partial representation; the agent may make targeted queries.

The wire version is separate from RGM versions, RepositoryGovernanceState v1 and any historical migration transport. An incompatible schema or reference algorithm requires a new wire/reference version and corresponding conformance vectors; no silent coercion.

## 4. Exact NativePath type (lossless)

`NativePath` is a disjoint tagged union:

```json
{"kind":"utf8","value":"."}
{"kind":"unix_bytes_base64","value":"Li4u"}
{"kind":"windows_wide_be_base64","value":"AC4="}
```

The latter two example values are **illustrative encodings**, not equivalent spellings of `.`. UTF-8 input converts to the platform's native path without case folding, Unicode normalization, trimming, alias inference or loss. On Unix native path units are raw `OsStr` bytes; on Windows they are exactly the big-endian bytes of the `u16` sequence emitted by `OsStr::encode_wide()`, matching the engine's existing `repository_state::path::os_units` convention. A mismatched native platform variant is rejected. Base64 uses RFC 4648 standard alphabet with padding and canonical re-encoding equality; reject malformed padding, unused nonzero pad bits, invalid NUL units, empty path and odd-length Windows bytes. Decode exact units; never use lossy Unicode conversions. Unsupported representability is a controlled error, not a fabricated alternative path.

Output MUST emit `utf8` when exact Unicode conversion is possible, otherwise the matching platform-native base64 form, and MUST preserve the same path identity. A readable display string, if supplied by an external client, has no identity authority. Exact path/root containment and observation are established by the engine, not by a second JSON path resolver.

A `NativePath` is a location representation, **not a global repository ID**. The RGS reference uses the resolved exact worktree root, not a remote URL or mutable branch reference.

## 5. Exact public observation/reference algorithm

Internal `RepositoryStateIdentity` contains framed observations and can include entire governed file bytes. **Never emit its raw bytes** in the public interface. Define `frame(x) = u64_be(length_of_x) || x`. Define `H(domain, parts)` as `SHA256(frame(UTF8("proto-ring-api01-v1")) || frame(UTF8(domain)) || u64_be(number_of_parts) || frame(part_1) || ... || frame(part_n))`. All SHA-256 outputs are 32 raw octets when used internally and lowercase 64-character hex when serialized. `u64_be` means eight exact big-endian octets. The scheme is versioned; a change to an identity's underlying domain representation requires an incompatible reference version, not a silent digest change. The byte-for-byte known-answer tests in `conformance/identity-vectors.json` are controlling **for this proposed public hash algorithm only**; they do not claim to be observed Rust engine-state digests.

* `repository_ref = H("rgs-repository-v1", [UTF8(platform), native_units(resolved_root)])`.
* `scope_ref = H("rgs-scope-v1", [repository_ref_raw, u64_be(scope_count), native_units(path_1), ..., native_units(path_n)])`, with exact RGS explicit-scope paths sorted by native-unit bytes, duplicate identities rejected.
* `state_ref = H("rgs-state-v1", [repository_ref_raw, scope_ref_raw, internal_rgs_repository_state_identity_bytes])`.
* Public RGS observation JSON: `{ "format":"proto-ring-rgs-ref-v1", "platform":"unix"|"windows", "repository":hex, "scope":hex, "state":hex, "coherence_basis":"ordinary_capture"|"host_established" }`.
* `ri_scope_ref = H("ri-scope-v1", [repository_ref_raw, u64_be(scope_count), native_units(path_1), ...])` over the **RI evaluation scope**, not the RGS scope.
* `ri_state_ref = H("ri-state-v1", [repository_ref_raw, ri_scope_ref_raw, internal_ri_state_identity_bytes])`.
* `ri_profile_ref = H("ri-profile-v1", [internal_profile_identity_bytes])`; `ri_context_ref = H("ri-context-v1", [internal_evaluation_context_identity_bytes])`.

A public result MUST expose the actual RGS root and explicit paths separately from these digests. A conditional request reference is **only a comparison hint**, never access or execution authorization; untrusted callers may forge its values. Comparable RGS references must have equal `format`, `platform`, `repository` and `scope`; their `state` fields are then compared. A mismatch in domain -> `incomparable_observation`; a mismatch in `state` alone -> `stale_observation`. Equal comparable values establish equality of the **contract-relevant observed state**, assuming cryptographic collision resistance; they do not establish global transactional coherence or absence of intervening A→B→A events. Return-to-A is acceptable between independent observations.

RGS, RI scope, profile, context and baseline/final RI identities are distinct domains. Do not compare across domains or claim that RGS and RI cover the same paths. An engine-created context identity **does not** prove the exact program or process environment that ran; it is not host admission. Claims of an isolated/coherent cut require independent host evidence that actually covers the claimed boundary. `coherence_basis:host_established` MUST NOT be populated solely because two ordinary captures compared equal. For direct local use where only standard capture is established, report `ordinary_capture` and do not assert absence of concurrent writers or in-evaluation ABA.

## 6. Structured values and inspection projections

`StructuredValue` is projected using the tagged `kind` union from `schemas/api.schema.json`: `null`, `boolean`, `integer` (`decimal` canonical signed decimal string, arbitrarily large), `string`, `sequence` and `mapping` (ordered `entries: [{key,value}]`). Preserve exact constructed meaning. Mapping keys MUST be unique; entries MUST be sorted by Rust/Unicode string lexical order. JSON Schema alone cannot enforce this uniqueness/order, so semantic tests MUST. Do not pass arbitrary-precision governance integers as IEEE-754 JSON numbers. Do not treat this wire tagged union as a new normative document syntax; accepted Structured Data YAML semantics remain authoritative.

`inspect` input `selector` is exactly one of: `all`, `bootstrap`, `model`, `authority`, `governed_objects`, `bindings`, `repository_integrity`, `projections`, `evidence_requirements`, or targeted `capability(id)`, `validation(id)`, `binding(id)`, `governed_object(target)`. Output includes RGS observation, resolved worktree root, explicit `scope_paths`, echoed selector and a typed `components` object. Full `all` MUST include all eight logical component keys, including explicit `absent` for each optional absent component. The mandatory bootstrap/model/authority/bindings cannot be represented as absent on a successful composed RGS. A targeted selector MUST only disclose the explicitly requested established component or subject; absent component -> `inapplicable`, missing subject in present component -> `not_found`.

Schema-backed component projections are: `bootstrap` (carrier path, loaded structured metadata and `repository_governance`), `model` (model version, logical provider and routed capabilities), `authority` (sources, roles, precedence), `governed_objects`, `bindings`, `repository_integrity` (consumer profile, order, full validations and safe profile reference), `projections` and `evidence_requirements`. Every carrier-backed component projection MUST include its exact loaded carrier `NativePath`, not merely the logical declarations; worktree root is already available at the inspection top level. RGS construction does **not** recursively validate every referenced product fact, run a generator or prove provider installation/evidence quality. Consumer IDs, relation strings, source roles and declared configuration values must not be interpreted beyond their owning contracts.

`explain` is a **deterministic typed query**, not LLM-generated normative prose. v1 supported subjects: authority role, declared authority precedence, governed object, validation, binding, projection, evidence requirement and capability. For authority roles, distinguish `authority`, `secondary_representation`, `non_authoritative`, `UNKNOWN_RESPONSIBILITY`, `UNDECLARED` exactly. Precedence is partial, not an invented total winner. `declaration` explanations return the queried subject and mechanically projected declared facts (tagged `StructuredValue`), never a claim of *why* consumer semantics are correct. Construction failures return stage errors; no explanation of a nonexistent partial state. A typed `UNDETERMINED` RI result has no invented cause if the engine has none.

The canonical RGS observation used by an in-process Rust `open` may be reused for `inspect` and `explain` on that loaded object. Separate CLI/JSON calls each perform an independent load; their observation references MUST be visible to prevent accidental conflation.

## 7. CheckRequest, host admission and effect-plan binding

`check_repository_integrity` input is exactly `{ "repository": NativePath, "expected_observation": ObservationReference|null }`. There is **no subset selection**, `command_prefix`, environment map, execution identity, privilege flag, executable path or untrusted host permit in this request. An absent `repository_integrity` capability is `inapplicable` **with no RI verdict**. A declared but missing/malformed required profile is a controlled RGS construction failure **with no partial state**. A valid empty profile preserves the existing RI engine's possible vacuous `PASS` and must disclose empty coverage; a valid `for_each` resolving to zero instances preserves `SATISFIED` without manufacturing a path-presence obligation.

**Mandatory pre-execution stages:** (1) host repository-access admission before protected disclosure; (2) canonical RGS load and optional comparable observation precondition; (3) host acceptance of the *actually loaded* consumer-owned profile; (4) host-controlled available environment realizations and **canonical engine** realization of all instances and command arguments; (5) host admission of the **complete executable effect plan**, including any forbidden *later* obligation, before the first validator; (6) engine-owned dispatch, guarded at each launch against executable, prefix, effective args, process environment, repository and required host guards; (7) existing RI evaluation, same-execution output capture, single result finalization. A forbidden later command refuses the **whole** check before any validator starts. The host cannot silently omit or reorder consumer obligations.

Conceptual Rust roles: `CheckRequest`, `AuthorizedRepository`, `CheckSubject`, `HostRealizations`, `ResolvedCheckPlan`, `AdmittedPlan`/`ExecutionPermit`, `ExecutionHost`, `OutputCustodian`. An admitted plan binds the exact worktree, profile/context identities, ordered concrete obligations (including zero-instance/unresolved entries), executable and environment effect set, and all required guards. An execution permit is invocation-bound and non-mintable by the public JSON/CLI agent request. The engine is the only expander and process runner. `EvaluationContextIdentity` (which omits executable prefixes and environment values) is *not* a substitute for actual host admission or toolchain attestation. A privileged host MUST control executable custody and untrusted repository code actually run with its credentials; merely allowlisting `cargo test`, using `env_clear` or trusting writable configuration is insufficient isolation.

**Direct local CLI v1:** commands use the OS permissions of the invoking process. `--local-context-file` selects a **local realization configuration**, not a privilege token. The default location is `$XDG_CONFIG_HOME/proto-ring/local-context.json` (or `$HOME/.config/proto-ring/local-context.json` if XDG_CONFIG_HOME absent) on Unix, `%APPDATA%\\proto-ring\\local-context.json` on Windows. Its typed format is `schemas/local-context.schema.json`: version `1`, declared repository, a list of unique environment realizations with `environment_id`, nonempty opaque `identity_base64`, nonempty ordered `command_prefix` and explicit `process_environment` string map. The referenced repository must resolve to the same worktree. An absent default file supplies an empty realization set (authorized missing realization -> canonical `UNDETERMINED`); a malformed existing file is `controlled_failure`/`local_context_invalid` before launching a consumer command. The direct local mode makes **no promise of sandboxing the invoking OS user**. Selecting an arbitrary local file by flag cannot activate a privileged mode. The binary does not elevate permissions, but an operator may deliberately start it under a powerful OS account; the corresponding effects are those of that account, not a sandbox guarantee.

**Delegated privileged integration:** available only through an independently controlled host using the Rust façade and its own protected execution boundary. The public CLI/JSON provides **no switch, filename or request field** to acquire privileged execution. The host must enforce actual separation/credentials/permissions, profile and executable substitution resistance and coherence basis when claimed. No universal VM, remote authorization server, global credential service or blanket execution timeout is required by API v1. Missing permission or mandatory guarantee -> `admission_refused` before any validator starts; a permitted missing/unavailable realization inside an authorized evaluation retains the engine's `UNDETERMINED`/`NON_PASS` result. Failure after effects began is `execution_incomplete`, not an invented pre-execution refusal or completed RI verdict. Do not retry automatically after unknown effects.

The existing RI state-capture, profile/context binding, ordering, prerequisite expansion, per-obligation status and `state_coherence_halt` remain authoritative. End-point identity equality is mandatory drift detection but not proof of a globally stable cut. The host's coherence guarantee must cover the claim it makes about both the governance inputs and the evaluated worktree, where relevant.

## 8. One CheckReceipt, output custody and no competing truth

Each admitted check attempt receives a random 32-octet identifier **before any command** (hex lowercase 64 characters); a `CheckReceipt` exists **only after** canonical engine completion and durable-enough host publication under its stated custody policy. Receipt ID is **not** an authorization token or content hash. Two runs against identical state still get different IDs. The receipt contains exactly one canonical RI verdict (`PASS` or `NON_PASS`), RGS observation, distinct RI profile/context references, RI scope, optional baseline/final RI state references, `state_relation` (`EQUAL`, `NOT_EQUAL`, `UNAVAILABLE`), `state_coherence_halt`, and the complete ordered validation/obligation result projection. An instance ordinal (`instance_index`) is **zero-based within its ValidationId** and is a canonical decimal `u64` string. Never invent a fourth RI status or a subset global PASS.

Every obligation includes actual `executed`, optional exit code, and two subordinate `StreamCapture` records. If no process started, both streams are `not_started` with absent observed/retained byte metrics, not `complete` zero. If a process started and emitted no bytes, the captured stream is `complete` with length zero. `stdout`/`stderr` are **untrusted bytes** of that invocation, potentially including credentials or adversarial instructions, never independent evidence that a consumer validation succeeded. A printed `All tests passed` cannot override engine `NON_PASS` due to governed-state drift. Source paths, original provider bindings and validation declarations retain their own authority; recorded strings do not acquire it.

The original engine currently sends validator stdout/stderr to `Stdio::null()`; v1 output capture requires **an extension to the engine-owned process-execution path**, not a second runner or a replay of validators. Capture both streams from the exact executed concrete obligation, including successful commands. Store bytes outside the evaluated governed repository scope under host control. Cap retained data at **64 MiB per stream** and keep the **last** 64 MiB on overflow, with original absolute byte offset and observed total when known. Drain concurrently to avoid pipe deadlocks; bound memory and on-disk staging. Do not silently drop bytes: expose `complete`, `partial`, `capture_failed`, `unavailable`, `not_started` plus explicit preserved range and lengths. If a descendant retains a pipe after the main validator has exited, capture MUST finalize without waiting indefinitely for EOF; drain currently available bytes where possible and mark incomplete when necessary. A capture-finalization rule is **not** a timeout applied to running consumer validators. Capture failure that could affect command behavior or make evaluation ambiguous must not be concealed as equivalent execution.

**Local default custody:** the receipt store is `$XDG_STATE_HOME/proto-ring/receipts` (or `$HOME/.local/state/proto-ring/receipts` when XDG_STATE_HOME is absent) on Unix, `%LOCALAPPDATA%\proto-ring\receipts` on Windows. These locations must resolve outside the governed worktree; if unavailable or not safely writable, deny check admission before command execution. Reject symlink/reparse-point substitutions; create user-owned directories/files with restrictive host-native permissions. Output retention target **7 days** (`604800` seconds), global retained-output quota **1 GiB**, per-stream tail retention **64 MiB**, maximum read **64 KiB**. Before finalization, under quota pressure, explicit partial/unavailable records are permitted and never mislabeled `complete`; after publication, the immutable receipt metadata is preserved under the stated policy, while output bytes may expire early with explicit retrieval `output_expired`. Receipt storage and outputs MUST be protected against path traversal, symlink substitution and unauthorized disclosure. Privileged hosts independently set their own access and retention policy; a raw receipt ID never bypasses access checking. `sha256_retained`, where present, is over the raw **retained** bytes, not over an invented complete stream and not proof of truth.

**Publication:** the host stages output capture, completes RI, finalizes capture metadata, writes one receipt manifest, and atomically publishes the finalized manifest before emitting a `result` response. The in-memory response is serialized from that **same finalized object**; it is not independently recomputed. Atomic rename does not itself guarantee durable persistence after power failure: any claimed durable receipt must additionally use the host's relevant fsync/durability mechanism. If the process crashes or finalization fails after potential effects, no fabricated completed receipt/verdict is emitted; a structured `execution_incomplete` response includes attempt ID and `effects_possible:true` *if the process can respond*. A dead process may emit nothing; the caller must not treat silence as evidence that no command ran. Recovery/retry of incomplete attempts is **not** implemented in v1.

## 9. Output retrieval exact semantics

`read_execution_output` request: `receipt_id` (64-char lowercase hex), `validation_id` (nonempty UTF-8 string), `instance_index` (canonical unsigned decimal `u64` string), `stream` (`stdout`/`stderr`), `offset` (canonical unsigned decimal `u64` string), `max_bytes` (JSON integer 1..65536). The four identifiers `receipt_id + validation_id + instance_index + stream` select **only a previously finalized original execution**. There is no arbitrary filesystem path in the request, no evaluator rerun, no re-observation and **no verdict** in the output-read response. Host access checks precede disclosure; `output_access_refused`, `output_expired`, `output_unavailable`, `output_not_started` and `subject_not_found` remain distinct.

If requested `[offset,offset+max_bytes)` overlaps the retained interval, return only the bytes from that requested interval in RFC 4648 canonical padded `data_base64`, with exact `returned_bytes`, `offset`, `retained_start`, `retained_bytes`, `observed_bytes|null`, `capture_state` and `next_offset|null` describing any further **retained** bytes. If offset lies before the retained interval or within a known missing gap -> `range_not_retained`, not a fabricated prefix. If beyond the complete known stream -> `invalid_output_range`; `offset` equal to the end of a complete empty or nonempty stream returns a valid zero-byte response. On an output stream marked `partial` with unknown total, the read may return retained bytes but MUST NOT imply the absent portion is zero or complete. The agent can request successive ranges and choose either or neither stream; no mandatory summaries or silent bulk copying into a single check result.

## 10. Rust implementation boundary and CLI contract

Suggested Rust crate: one `proto-ring-api` package with a public library and one `proto-ring` binary, delegating to `proto-ring-engine`. The library contains a typed `GovernanceObservation` holding the single successfully composed RGS, and public equivalents of `discover`, `open`, `inspect`, `explain`, `check_repository_integrity` and `read_execution_output`. All execution admission and custody are host traits/injected, with type-states/nonforgeable API objects as appropriate; no duplicate governance parser, selector, authority resolver, state capture or command runner. No production implementation is authorized by this draft alone.

Standalone commands (candidate stable grammar):

```text
proto-ring json [--local-context-file NATIVE_PATH]  # one JSON request from stdin
proto-ring discover --json
proto-ring inspect --repository NATIVE_PATH --selector NAME --json
proto-ring inspect --repository NATIVE_PATH --selector-json JSON --json
proto-ring explain --repository NATIVE_PATH --query-json JSON --json
proto-ring check --repository NATIVE_PATH [--local-context-file NATIVE_PATH] [--expected-observation-json JSON] --json
proto-ring output --receipt HEX64 --validation ID --instance U64DEC --stream stdout|stderr --offset U64DEC --max-bytes INT --json
```

`NAME` is one of the nine non-parameterized `InspectSelector.kind` forms (see schema). `--selector-json` and `--query-json` are exactly one JSON object each matching the wire selector/query schema; unknown CLI flags or ambiguous duplicate flags fail. `--repository` must preserve the OS-native argument spelling (`args_os`) and pass through the canonical root resolver; the JSON path variants remain available to clients requiring exact non-UTF-8 handling. No check or output operation is executed by `inspect`, `explain` or `discover` as a side effect. `proto-ring json` may apply `--local-context-file` **only** to the nonprivileged local realization mode; it never confers a security capability. The CLI is a thin syntactic adapter to one shared engine-backed public API, not a second semantics layer.

## 11. JSON Schema and conformance responsibilities

The JSON Schema Draft 2020-12 documents in `schemas/` describe **syntactic** shapes, discriminants, closed fields, types and ranges. `api.schema.json` owns shared definitions; `request.schema.json`, `response.schema.json` and `local-context.schema.json` reference them using stable URNs (no network retrieval). A client can use a `jsonschema` library or generate a Zod validator from the accepted public schema, but **Zod is optional** and cannot become a second normative contract. Rust `serde` deserialization must agree with the same accepted semantics. `schemars` may assist generation if the generated output is checked against the accepted versioned schema, not silently treated as authority.

**Not expressible solely in JSON Schema:** raw duplicate-key rejection, canonical Base64 pad bits, OS native path validity, `u64` maximum, unique/map key ordering for tagged StructuredValue, relationship of request/response selectors to exactly the published result, RGS component required-presence rules, RI validation order/prerequisite semantics, token computation, host admission, actual executable provenance, RI result aggregation, output capture completeness and absence of effects. Each needs explicit executable conformance/hostile tests.

`conformance/identity-vectors.json` holds 8 deterministic known-answer public-reference hashing vectors; `conformance/schema-cases.json` contains **illustrative schema shape** cases; `conformance/semantic-cases.json` lists unresolved **runtime acceptance tests**.
